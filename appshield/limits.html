What this catches — and what no scanner can

Most compliance tools oversell. Here is the plain version: static analysis reads your source files, so it can only catch problems that are visible in source files. In our own audit of current Apple and Google requirements we counted 24 requirement types that no source-code scanner can see — including ours. Knowing the boundary is what makes the rest of the scan trustworthy.

What a scan CAN catch

  • Outdated target SDK — targetSdk below Google's current requirement (API 36), read straight from your gradle files.
  • Outdated Play Billing Library — v6/v7 dependencies that Play now rejects; v8+ is required.
  • Missing required declarations — App Tracking Transparency usage without the ATT prompt, missing privacy-manifest / Required Reason API declarations (the ITMS-91053 rejection), missing export-compliance keys, missing account-deletion affordances in code.
  • Hardcoded secrets — API keys, tokens, and private keys sitting in source.
  • Insecure network patterns — cleartext HTTP allowances, disabled certificate validation.
  • Payment-policy red flags — third-party payment SDKs wired to digital-goods purchases that store policy routes through the platform's billing.
  • Deprecated / forbidden API usage — calls the stores have announced they block or will block.

What NO scanner can catch (ours included)

  • Metadata accuracy — whether your store listing, title, and description honestly describe the app. Human reviewers judge this.
  • Screenshot content — outdated, misleading, or non-compliant store screenshots.
  • Privacy nutrition labels — whether the data-collection labels you filled in at submission match what your app actually does.
  • Runtime behavior — crashes, broken flows, content that only appears when the app runs. Store review runs your app; a scanner doesn't.
  • Server-side data handling — what your backend does with user data is invisible to a client-code scan.
  • Purchase flows as experienced — whether your IAP flow is confusing, misleading, or violates pricing-display rules in practice.
  • Age-rating correctness — whether the rating questionnaire you filled in matches your content.
  • …and the rest of the 24 — review-time judgment calls (design quality, spam/duplication policy, content policy) that exist precisely because they need a human.
So what is a scan actually worth? It's a pre-flight lint: it clears the class of rejections that are mechanical, current, and visible in code — the ones that waste a review cycle on something a regex could have told you. It is not a promise you'll pass review, and any tool that sells "compliance guaranteed" is selling past this boundary.

How the rulebook stays honest

Every rule in AppShield's registry carries provenance: the exact guideline section it cites, a link to the official source, the date it was last verified, and a status. Rules that are genuinely store-cited are labeled active (56 of 86 today); rules that are good engineering practice but not store law are labeled best practice (30 of 86) instead of being dressed up as citations. When a store changes its policy, the rule changes or it dies — staleness is the failure mode this whole design exists to prevent.
