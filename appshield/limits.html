Scope & limits

What this catches, and what no scanner can catch

Static analysis reads your source files, so it can only catch problems that are visible in source files. Our own audit of current Apple and Google requirements counted 24 requirement types that no source-code scanner can see, including ours. This page draws that line.

What a scan CAN catch

Build configuration

  • Outdated target SDKtargetSdk below Google's current requirement (API 36), read straight from your gradle files.
  • Outdated Play Billing Libraryv6/v7 dependencies that Play now rejects. v8+ is required.

Security

  • Hardcoded secretsAPI keys, tokens, and private keys sitting in source.
  • Insecure network patternsCleartext HTTP allowances, disabled certificate validation.

Store declarations

  • Missing required declarationsApp Tracking Transparency usage without the ATT prompt, missing privacy-manifest or Required Reason API declarations (the ITMS-91053 rejection), missing export-compliance keys, missing account-deletion affordances in code.
  • Payment-policy red flagsThird-party payment SDKs wired to digital-goods purchases that store policy routes through the platform's billing.
  • Deprecated or forbidden API usageCalls the stores have announced they block or will block.

What is a scan actually worth?

It's a pre-flight lint. It clears the class of rejections that are mechanical, current, and visible in code, the ones that waste a review cycle on something a regex could have told you. It is not a promise you'll pass review, and any tool that sells "compliance guaranteed" is selling past this boundary.

How the rulebook stays honest

Every rule in AppShield's registry carries provenance: the exact guideline section it cites, a link to the official source, the date it was last verified, and a status. Rules that are genuinely store-cited are labeled active (56 of 86, verified 2026-08-29); rules that are good engineering practice but not store law are labeled best practice (30 of 86) instead of being dressed up as citations. When a store changes its policy, the rule changes or it dies. Staleness is the failure mode this whole design exists to prevent.
